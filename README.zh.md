# brkpt-auth

[English](./README.md) | 简体中文

面向 NestJS 的透明、可组合、可移植、六边形认证方案。不是样板项目，也不是库。

---

## 设计理念

为项目添加认证功能通常有四种常见方式，每一种都有其真实代价。

**托管服务**以托管 API 的形式运行认证。接入速度很快，但你的数据库结构、会话模型（传统 session、无状态 JWT，还是有状态 JWT）、令牌传输方式（cookie 还是 header）以及 JWT payload 的形状，全部由服务商掌控，你这一侧完全看不到这些细节。你还要放弃数据所有权，并承担供应商锁定的风险。

**自托管库**以 npm 包的形式运行在你自己的基础设施上，数据留在你手里。但核心设计依然是固定且高度抽象的：定制任何东西都要先弄懂库的内部模型，超出这个模型的需求即便有插件机制也很难甚至无法满足。代码虽然就放在本地的 `node_modules` 里，但这并不会让内部实现更容易读懂或修改。

**样板项目**会给你完整的源代码，但这些代码是为某一种特定的用户模型、数据库和项目结构写的。凡是和你项目不匹配的地方都要返工。样板项目常常被宣传为可直接用于生产、易于扩展，但在它之上继续开发，通常会暴露出紧耦合、架构边界不清、结构冗余、可读性差、功能缺失等问题，而且这类问题更难排查，因为这些代码本来就不是你设计的。下一个项目又要重新经历一次同样的评估和返工。

**自行开发**给你完全的控制权，但代价同样真实：没有共享的约定可以用来检验你的实现，逻辑容易散落在代码库各处，一些能力很难干净地实现，一个新需求可能迫使你做一次大的架构调整，而不只是一次小的添加。每个新项目都要从同样的起点重新开始。

## 为什么选择 brkpt-auth

brkpt-auth 不是样板项目，也不是库。它围绕你自己实现的接口构建，而不是一个直接可用、带有预设主张的默认实现：

- **透明** — 完整源代码直接安装进你的项目。没有编译产物，没有隐藏行为。
- **可组合** — 功能相互独立。只添加你需要的部分。
- **非侵入** — 不对你的数据库结构、用户模型或 JWT payload 做任何假设。
- **可移植** — 业务逻辑与适配器相互独立。迁移到新项目只需替换适配器。
- **原生适配 NestJS** — 从一开始就围绕 NestJS 的模块、依赖注入、守卫、装饰器和 provider 构建。
- **六边形架构** — 服务持有业务逻辑，端口（port）定义契约，适配器（adapter）完全由你掌控。没有层层嵌套的 domain/infrastructure 分层需要翻找。

## 工作原理

服务依赖一个抽象接口，也就是端口（port），你通过实现它来编写适配器（adapter）。这是你的基础设施唯一接触认证逻辑的地方。除了 `core` 之外，各个功能之间互不依赖，所以你只需添加需要的部分，不必触碰其余代码。`BrkptAuthModule` 只需在 `AppModule` 中注册一次，就会自动完成所有装配，不需要你手动注册和拼接 provider。

这正是它不会像样板项目那样变得臃肿的原因。你能获得清晰的定制入口，同时保持容易上手。

`brkpt-cli` 会将源代码安装进你的项目。你实现适配器并在 `features.ts` 中列出它们；大多数适配器方法只是简单的字段映射或对你现有代码的直接调用。

## 如何使用

每个功能都遵循同样的流程：用 `brkpt-cli` 添加它、实现它的适配器、在 `features.ts` 中注册它。完整的代码演示可参考[快速开始指南](https://brkpt.com/auth/zh/guides/get-started/)。

## 功能

| 功能              | 说明                                 |
| ----------------- | ------------------------------------ |
| `core`            | 无状态 JWT 双令牌认证。**必需**。    |
| `credentials`     | 基于密码的注册与登录                 |
| `oauth`           | 第三方登录                           |
| `otp`             | 一次性密码认证与验证                 |
| `magic-link`      | 魔术链接认证与验证                   |
| `session`         | 在无状态 JWT 基础上叠加的会话管理    |
| `blacklist`       | 实时访问令牌吊销                     |
| `verify-email`    | 邮箱验证门槛——未验证账户在验证前受限 |
| `change-password` | 已登录状态下的密码修改               |
| `reset-password`  | 通过身份证明重置密码                 |
| `audit`           | 用户自定义的关键认证事件处理器       |

## 仓库结构

```plain
brkpt-auth/
 ┣ demo/     # 完整可运行的 NestJS demo 项目
 ┗ lib/      # 供 brkpt-cli 拉取安装到你项目中的源代码
```

### 运行 demo

将 `.env.example` 复制为 `.env` 并填入相应的值，然后：

```bash
cd demo
pnpm install
pnpm start:dev
```

demo 使用内存用户存储，但需要一个本地 Redis 实例。E2E 测试在内存中模拟了 Redis 和邮件服务，因此不需要任何外部服务。

```bash
pnpm test        # 单元测试
pnpm test:e2e    # e2e 测试
```
